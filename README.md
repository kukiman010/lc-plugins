# lc — плагин «жизненный цикл задачи» для Claude Code

Плагин даёт две команды. Они проводят задачу через одну и ту же цепочку:
**план → ваше «да» → исполнение → проверка → исправления**.
Основная сессия в этой цепочке только раздаёт работу (диспетчер): сама код не пишет и
ничего не меняет, пока вы не одобрите план.

| Команда | Когда использовать |
|---|---|
| `/lc-implement <задача>` | одна понятная задача |
| `/lc-orchestrate <список или файл спецификации>` | список задач или большая задача, которую надо разрезать на части |

## Установка

```
/plugin marketplace add kukiman010/lc-plugins
/plugin install lc@lc-plugins
```

Обновление: `/plugin marketplace update lc-plugins`.

## Из чего состоит

```
.claude-plugin/
  plugin.json        — описание плагина (manifest): имя, версия
  marketplace.json   — превращает этот репозиторий в маркетплейс, чтобы ставить из git
commands/
  lc-implement.md    — команда для одной задачи
  lc-orchestrate.md  — команда для списка задач
agents/
  lc-planner.md      — планировщик
  lc-worker.md       — исполнитель
  lc-reviewer.md     — проверяющий
```

### Агенты (subagents — отдельные помощники со своим контекстом)

**lc-planner — планировщик** (модель opus)
- Работает только с планом: ничего не реализует и не коммитит.
- Прежний план из `.claude/tasks/` переносит в `.claude/tasks/archive/<дата-время>/` (не удаляет).
- Сверяет план с кодом, ничего не придумывая: каждый файл в плане проверен поиском, для
  нового кода указан образец `path:line` (Mirror), команды проверки взяты из реальных
  build-файлов, скриптов или CI (автоматических проверок в репозитории).
- Если от неясного места в запросе зависит результат, задач не пишет и возвращает `QUESTIONS`.
  Мелкие решения принимает сам и записывает в раздел `Assumptions`.
- Режет работу на срезы (slices — маленькие самостоятельные шаги, обычно до ~5 файлов).
  Срез может зависеть только от более ранних срезов, и после каждого проект остаётся рабочим.
- Пишет `.claude/tasks/plan.md` (чек-лист и допущения) и по файлу `NNN-slug.md` на каждый срез.

Поля файла задачи:

| Поле | Смысл |
|---|---|
| Goal | цель одной фразой |
| Depends on | от каких срезов зависит |
| Files | пути (новые помечены `(new)`) |
| Mirror | образец в коде, на который опираться |
| Done when | проверяемый результат |
| Gate | реальная команда проекта (сборка, тест), которую запустит проверяющий |
| Forbidden | что в этом срезе трогать нельзя |

**lc-worker — исполнитель** (модель как у сессии)
- Делает ровно один срез и не берёт следующий.
- Вносит минимальное изменение, переиспользует то, что уже есть в проекте, и следует `CLAUDE.md` проекта.
- Сам запускает Gate и отчитывается: какие файлы изменены, какая команда запускалась, прошла ли она.
- В раунде исправлений чинит только пункты из списка must-fix. Не коммитит.

**lc-reviewer — проверяющий** (модель как у сессии)
- Физически не может править файлы: у него нет Edit и Write.
- Смотрит реальный `git diff` и `git status` и верит диффу, а не рассказу исполнителя.
- Сам перезапускает Gate.
- Проверяет, достигнута ли цель, проходит ли Gate, соблюдены ли правила проекта и нет ли работы вне среза.
  Стиль, имена, производительность и безопасность не оценивает.
- Первая строка ответа — строго `VERDICT: ok` или `VERDICT: must-fix`, для must-fix дальше идёт нумерованный список.

## Как работает `/lc-implement`

1. **План.** lc-planner пишет один файл задачи.
   - `QUESTIONS` — вы получаете вопросы, отвечаете, планировщик перезапускается.
   - `NEEDS ORCHESTRATE` — задача слишком большая; команда покажет предложенные срезы и посоветует `/lc-orchestrate`.
   - Если передать готовый `.claude/tasks/NNN-*.md`, планировщик пропускается.
2. **Ваше «да».** Вы видите файл задачи целиком. Пока не ответите «да», никто ничего не правит. Если есть правки, план переписывается.
3. **Цикл.** worker → reviewer → при `must-fix` снова worker с этим списком → reviewer. Не больше 2 раундов исправлений.
4. **Отчёт:** задача, команда Gate и её результат, вердикт, сколько ушло раундов. Без коммита.

## Как работает `/lc-orchestrate`

1. **План.** lc-planner режет запрос на срезы в `.claude/tasks/`. Вопросы обрабатываются так же, как в `/lc-implement`.
2. **Ваше «да».** Вы видите список задач с зависимостями и допущения.
3. **Каждый срез по порядку:** worker → reviewer → до 2 раундов исправлений.
   - Если после 2 раундов срез всё ещё must-fix, весь запуск останавливается, и следующие срезы не трогаются.
   - Если ok, в `plan.md` ставится галочка и сохраняется точка отката:
     `git stash create` + `git stash store` (рабочая папка при этом не меняется).
     Откат: `git stash list` → `git stash apply stash@{N}`.
     Новые неотслеживаемые файлы в этот снимок не попадают.
4. **Специалисты (по желанию).** Если установлен ECC: срезы про авторизацию, секреты и пользовательский ввод
   дополнительно проверяет `ecc:security-reviewer`, а срезы про скорость — `ecc:performance-optimizer`.
   Серьёзные находки считаются must-fix и расходуют те же 2 раунда.
5. **Итог:** что сделано, где застряло, какие проверки запускались, какие точки отката сохранены.
   Без коммита, `.claude/tasks/` не удаляется.

## Что можно настроить

- **Число раундов исправлений** — строка `Max fix rounds` в `commands/*.md`.
- **Модель планировщика** — поле `model:` в `agents/lc-planner.md`.
- Команды прямо запрещают подключать brainstorming, writing-plans, orch-* и prp-*,
  чтобы другие плагины (superpowers, ECC) не перехватили задачу своим циклом.

## Заметки

- Коммитить результат после работы нужно самостоятельно: плагин этого никогда не делает.
- Если раньше команды и агенты лежали в `~/.claude/commands` и `~/.claude/agents`,
  после установки плагина эти копии нужно удалить, иначе они будут дублироваться.
